# Poll posts

Updated 19 November 2026. Contract snapshot: `1a16eed` on `staging`, including the final poll behavior from migrations `088`–`090`.

## 1. Access and data structure

Use a Supabase client authenticated as the acting user. Server-rendered reads and server actions must preserve that user's session and authorization context. **Do not use a service-role client for poll creation, results or voting.** Poll tables are private; their RLS and grants deliberately prevent direct client reads/writes. Use the public RPCs below rather than querying votes or calculating results from raw rows.

Polls extend ordinary posts; the question is stored in `posts.body`. There is no separate question field, `posts.type` flag or client-created poll table to add.

| Table | Fields and meaning |
| --- | --- |
| `posts` | Existing post identity, `body` question, `userId` author, `groupId` audience (`null` for the global feed), `file` (`null` for a poll). Normal comments, likes and post-opening behavior remain attached to this post. |
| `post_polls` | `post_id` bigint primary key referencing `posts.id`; `duration_hours`; `created_at`; `ends_at`. One poll per post. Deadline equals creation time plus the selected duration. |
| `post_poll_options` | `id` bigint, `post_id`, `position` (1–4), `label`. Positions are contiguous and determine display order. Labels are unique within a poll, ignoring case after whitespace normalization. |
| `post_poll_votes` | `id` bigint, `post_id`, `option_id`, `user_id` UUID, `created_at`. One vote per account per poll, and the option must belong to that poll. Voter identities are not exposed in the result API. |

Deleting the source post cascades to the poll, options and votes through the existing authorized post-deletion flow. Deleting a voter's Auth account anonymizes its vote (`user_id = null`) and preserves totals. There is no vote-removal or change-vote API.

Post, option and Frequency IDs are PostgreSQL bigints. RPC projections return identities as **decimal strings**. Keep them as strings in state, RPC arguments, URLs and JSON; never round through JavaScript `Number`. Operation `p_request_id` is a UUID generated by the client.

## 2. Creation rules

- A nonblank question is required, up to **20,000 Unicode code points**. Use `Array.from(body).length` for client validation rather than UTF-16 `body.length`.
- Provide **2–4 options**, each 1–100 Unicode code points after normalization. Collapse runs of whitespace and trim the ends; reject empty/duplicate labels and control characters. The server revalidates the canonical labels.
- Allowed durations are **24, 72 or 168 hours** (1, 3 or 7 days). The server sets creation time and deadline; clients do not submit dates.
- A post contains a poll **or** an image/video/file attachment. Poll publication has no file parameter, and the stored `posts.file` is null. Disable attachment selection while a poll is selected, and vice versa.
- The **question, options, duration and audience are immutable after publication**. Do not offer Edit for a poll, convert it into an ordinary post, move it to another Frequency, attach media or extend its deadline. This also prevents changing the meaning of votes later.
- The post author can vote, under the same rules as other eligible users; authors do not see early percentages just because they own the post.
- Polls are available in the global feed and public/private Frequencies. Creating or voting in a Frequency requires current joined membership, including for a public Frequency. Viewing follows the post's existing visibility rules.
- Authentication, onboarding/account eligibility, Business publication eligibility, block rules and current Frequency access are checked by the existing shared helpers. Do not duplicate a weaker permission model or infer authorization from a previously cached post.

### Atomic publication

```ts
// Generate once for this intended publication. Retain the complete payload
// and UUID until success is confirmed or the operation is abandoned safely.
const requestId = crypto.randomUUID();

const { data, error } = await supabase.rpc('create_post_with_poll', {
  p_body: 'Which day works best?',
  p_options: ['Friday', 'Saturday'], // JSON array of strings, not option objects.
  p_duration_hours: 24,
  p_request_id: requestId,
  p_group_id: null, // Global feed; otherwise the Frequency ID as a string.
  p_mentions: [],  // Selected question mentions; same entity contract as posts.
});

if (error) {
  // Handle the error before using data; see retry rules below.
} else {
  // data: { id, body, file, revision, mentions, poll }
  // id is a decimal string, file is null, poll is the projection in section 4.
}
```

The RPC creates the post, poll, options, mention references and any eligible mention notifications in one transaction. Do not insert `posts` first and then call a second operation to attach a poll.

`p_group_id` defaults to null and `p_mentions` defaults to `[]`. Mentions apply to the **question/post text**, using the existing selected-user entity format `{ user_id, start, end, label }`, Unicode-code-point positions and audience restrictions from **Chat, notifications and mentions**. Option labels are plain text, not separate mention sources.

The publication response includes the existing mention editor snapshot (`revision` and references) plus `poll`; this does not make published poll questions editable.

## 3. Loading polls alongside posts

Continue fetching posts through their existing authenticated feed/detail APIs, then batch-hydrate their poll metadata:

```ts
const { data: polls, error } = await supabase.rpc('get_post_polls', {
  p_post_ids: postIds, // Decimal strings; at most 50 IDs per call.
});
```

- The result is an array of authorized poll projections. Associate entries with posts by `post_id`; do not depend on array order.
- Ordinary posts have no entry. Unavailable/inaccessible polls are also omitted. Do not expose which private poll exists by performing privileged fallback reads.
- The question stays in the ordinary post body; the poll projection contains its options/state, not a second copy of the question.
- An RPC/network error is **not** proof that the post has no poll. Keep existing content where safe, show a retryable poll-loading error, and do not enable editing or replace it with an ordinary-post state based on a failed lookup.
- A previously displayed poll that is now omitted after a successful authorized read is unavailable. Remove its poll content/actions and reconcile the source post/access state; do not keep showing private cached results indefinitely.
- Apply the same hydration in feeds, Frequency feeds, profile post lists and post detail/notification destinations wherever posts are rendered.

## 4. Result projection and visibility

```ts
type PollView = {
  post_id: string;
  duration_hours: 24 | 72 | 168;
  created_at: string;
  ends_at: string;
  server_time: string;
  is_closed: boolean;
  can_vote: boolean;
  selected_option_id: string | null;
  results_visible: boolean;
  total_votes: number;
  options: Array<{
    id: string;
    position: number;
    label: string;
    votes: number | null;
    percentage: number | null;
  }>;
};
```

| Viewer state | Option display | Footer/actions |
| --- | --- | --- |
| Has not voted, poll open | Labels only. `votes` and `percentage` are null; no result bars/percentages. | **Always show `total_votes`**, including 0. Voting enabled only when `can_vote` is true. |
| Has voted, poll open | Selected option highlighted; counts, percentages and result bars available. | Live total and remaining duration; no changing/removing the vote. |
| Poll ended | Results available to every authorized viewer, even someone who never voted. | Total and `Poll ended`; all vote actions disabled. |
| Can read but cannot vote | Respect the same own-vote/expiry result gate; no privileged early breakdown. | Show the total; disable voting. For example, a public-Frequency visitor may be able to read without being a joined member. |

`results_visible` becomes true when the viewer has voted **or** the poll has ended. A total visible before voting is intentional; it is not permission to reveal per-option counts. Use the server's percentages, rounded to one decimal place; independently rounded percentages can sum slightly above/below 100. A poll with zero votes returns zero percentages once results are visible.

These fields are personalized. Never share/cache one user's `selected_option_id`, `can_vote` or visible breakdown as another user's response, including through server/CDN caches. Scope runtime state to the account and sign-in generation and clear/ignore it on logout or account switching.

## 5. Voting, retries and failures

```ts
const { data: poll, error } = await supabase.rpc('vote_post_poll', {
  p_post_id: postId,
  p_option_id: optionId,
});
// Success returns one canonical PollView, not an array or a raw vote row.
```

One account may cast one final vote. Retrying the **same option** is idempotent and returns the current projection, including after the deadline if that vote was already saved and the user still has access. Trying a different option after a saved vote is rejected. The server serializes conflicting attempts and owns deadline/permission checks.

For smooth feedback, highlight the chosen option immediately as pending and disable additional choices while submitting. Reveal percentages/update total together from the successful server response; do not fabricate a breakdown from the visible total. Keep the selected state visually distinct from an unconfirmed submission.

If a response is lost or times out, retain that exact option and offer **Retry vote** for the same option. Do not allow a different choice while the original outcome is uncertain. Reconcile with an authorized read; clear uncertainty when a stored selection is confirmed. A definitive closed/ineligible/final-vote response should refresh state rather than loop on the failed action.

For **publication** uncertainty, retain the exact `p_request_id` and every argument (question, ordered options, duration, audience and mentions). Retrying returns the same post. Do not generate a new UUID on Retry or reuse the UUID for a changed payload; the operation namespace is shared with ordinary post publishing.

| Error message | Handling |
| --- | --- |
| `POLL_INVALID_POST`, `POLL_INVALID_OPTIONS` | Validate the question, duration, audience and option input; show a useful validation message. |
| `POLL_INVALID_PAGE`, `POLL_INVALID_VOTE` | Invalid read/option arguments; refresh stale options or correct the request. |
| `POLL_IMMUTABLE` | Published poll content/configuration cannot be edited. |
| `POLL_CLOSED` | Disable choices and refresh final results. |
| `POLL_VOTE_FINAL` | A different choice is already stored; refresh and display the canonical selection. |
| `POLL_RETRY_MISMATCH` | Publication UUID belongs to another payload/actor. Do not silently create a replacement operation after an uncertain save. |
| `POLL_UNAVAILABLE`, `MENTION_UNAVAILABLE` | Current account/source/membership permissions do not allow the operation. Fail closed and reconcile access. |
| `POLL_REQUIRES_READ_COMMITTED`, `MENTION_REQUIRES_READ_COMMITTED` | Unsupported custom transaction isolation; ordinary independent Supabase RPC requests use the expected boundary. |
| Transport error/timeout or malformed success | Outcome can be uncertain. Preserve publication identity or selected vote and offer a safe retry. |

Mention validation errors can also be returned when the question contains selected mentions. Use the existing mention error handling. Always inspect Supabase `error` before treating `data` as success; do not expose raw database errors to users.

## 6. Live results

Live updates use **private Supabase Broadcast**, not raw `postgres_changes` subscriptions on poll/vote tables.

- Topic: `poll:post:<postId>`.
- Event: `poll_changed`.
- Payload: `{}` — a content-free invalidation hint, with no counts, options, voter IDs or question.
- The database emits the event after a committed vote insertion. Same-choice retries do not create another vote/event.
- Any currently source-authorized viewer can join, including an unvoted viewer. On a hint, call `get_post_polls` again under that viewer's session and replace/reconcile the canonical projection.

Minimal subscription wiring, using the same authenticated client:

```ts
await supabase.realtime.setAuth(); // Current signed-in client's token.
// Confirm the initiating login is still current after this await.
const channel = supabase
  .channel(`poll:post:${postId}`, { config: { private: true } })
  .on('broadcast', { event: 'poll_changed' }, () => {
    scheduleAuthorizedPollRefresh(postId);
  })
  .subscribe(status => {
    if (status === 'SUBSCRIBED') scheduleAuthorizedPollRefresh(postId);
  });

// On unmount/invisibility/background/logout, when no viewer still owns it:
// await supabase.removeChannel(channel);
```

`scheduleAuthorizedPollRefresh` is application code that coalesces hints and calls the read RPC; it is not a database function. The example is wiring only: the lifecycle owner must implement current-session fencing, reconnect/error handling and cleanup.

Match these lifecycle/concurrency rules:

1. Share one channel per poll/current login across simultaneous feed/detail viewers using reference-counted ownership. Subscribe while a poll is visible and its page is active; unvoted viewers need the channel for live totals too.
2. Coalesce bursts (Mobile uses about 75 ms), avoid overlapping aggregate reads and remember one pending refresh when hints arrive during a read or vote.
3. An aggregate read started before/during the user's vote must not overwrite its acknowledgement or clear its confirmed selection. Settle the vote, then run one fresh read to reconcile concurrent votes.
4. Ignore stale/out-of-order responses, including responses from a prior login. Within one available poll, accepted snapshots must not reduce confirmed totals or remove a confirmed selection.
5. Fetch on initial subscription/reconnection, return to the page/window and network recovery. Reconnect with bounded backoff. A quiet 60-second recovery read while visible supplements socket events; it is not the primary update mechanism or a 15-second polling loop.
6. Remove subscriptions and timers when inactive or no longer needed. Clear per-login state on account transitions, and never install an old explicit access token globally after a delayed await.

An unvoted viewer sees **only the total change**. A viewer who has voted sees the updated percentages **and** total. Opening results after expiry works for both.

Channel authorization is checked on join; it is not a substitute for the current-access checks on every result fetch. A revoked member's already-joined socket can temporarily receive an empty hint; no private results may be rendered from that hint or a privileged fallback read. Do not publish raw poll tables, add permissive Realtime policies or send client-authored `poll_changed` events.

## 7. Deadline and presentation

Use `ends_at` together with `server_time` for a server-relative countdown. Preserve the elapsed-time anchor for that snapshot across visibility changes, preferably using a monotonic clock. Reusing an old `server_time` with a newly reset local origin incorrectly extends the displayed duration.

At the deadline, disable voting locally and fetch again to reveal the server-confirmed final projection. **Expiry itself does not emit a vote broadcast**; it is computed on reads. Also reconcile on return from a background tab/page. If expiry refresh fails, keep voting disabled and offer Refresh results rather than inventing final counts. The server remains authoritative even if a client timer is wrong.

Keep option positions stable; use a small, smooth selected/result-fill transition (Mobile uses approximately 220 ms) and respect reduced motion. Show the total and remaining time/ended state in a compact footer. Do not add the explanatory **Votes are final** footer text. Show inline submission/error/retry feedback without replacing the whole post with a spinner. Loading skeletons should match the visible poll geometry.

## 8. Notifications and ordinary post behavior

Poll creation with question mentions uses the normal post-mention notification pipeline. Eligible recipients get the existing `postMention` in-app/push behavior, subject to permissions/preferences and lifetime mention deduplication. Do not send a second poll-specific notification or create notifications in the client.

Casting a vote creates **no vote notification or push**. Live results are supplied by the private broadcast/read flow. Ordinary comments and mentions in comments on the poll post continue through existing comment APIs and notification/highlight routing. Polls themselves are posts, not comment attachments.

## 9. Functional checks

1. Create global, public-Frequency and private-Frequency polls with 2–4 options and each supported duration. Check empty/duplicate/oversized options and poll/media exclusivity.
2. Verify public-Frequency nonmembers can only use the visibility allowed by the source and cannot vote; private outsiders/pending invitees cannot read poll content/results or subscribe.
3. Before voting, every eligible viewer sees the live total, with no percentages. Author has the same early-results restriction.
4. Vote on device A; unvoted device B receives a live total change only. After B votes, both devices receive live total/breakdown updates without manual refresh.
5. Retry the same vote/publication after a lost response: one vote/post only. A different vote fails; changing an uncertain publication payload/UUID must not silently duplicate it.
6. Check expiry with and without a prior vote, zero-vote results, return after tab/background suspension and a failed expiry refresh.
7. Published question/options/duration/audience cannot be edited and media cannot be attached; ordinary nonpoll post editing continues to work.
8. Check blocked/departed/banned account access, logout/account switching, reconnect, multiple visible copies of the same poll and out-of-order vote/refresh responses.
9. Mention someone in the question; verify the normal notification opens the same poll post without duplicate alerts. Comments and comment mentions retain their normal behavior.
